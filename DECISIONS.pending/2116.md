### Amendment of decision 60: two adapter ids are compared by the datasource their engines really get

Proposed by story 2116 on 2026-11-10, as an amendment of decision 60. Not decided yet.

Decision 60 lets an adapter id without `data-source-name` run on a bean `camundaBpmDataSource`. The
startup check which keeps two embedded engines off one database read only the keys. So it missed two
setups where two ids share a database:

- an id without the key, which runs on `camundaBpmDataSource`, and an id with
  `data-source-name: camundaBpmDataSource`
- an id without the key, which runs on the application's default datasource, and an id which names
  that datasource by its bean name, such as `dataSource`

On Spring Boot the check now compares what each engine really runs on. The engine holder knows the
datasource once it chose it. The application's default datasource, the one Spring injects by type,
has no name in this comparison. Every other datasource is named by its bean name, so an alias and the
bean name compare equal as well. The table prefix is still read from the key.

The same comparison feeds the check across adapter types (decision 47). A fork adapter which builds
its identity from the keys still describes the default datasource the same way, so a `camunda7` id
and a fork id on the default datasource still compare equal. Quarkus is not touched. It has no
`camundaBpmDataSource`, and it names its datasources in the configuration.

Proposed text to add to decision 60, after the paragraph which starts with "What the engine does
then follows the datasource it really runs on":

> The check that two adapter ids do not share a database (decision 47) follows the datasource too. It
> compares the bean name of the datasource each engine got, and the application's default datasource
> counts as one datasource however it was reached.
