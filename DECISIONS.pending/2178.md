### A switch set at task level ends the start

Decided by the maintainer on 2026-11-14: a key nobody reads ends the start, always.

This changes one passage of decision 20.

- Decision 20, the paragraph which starts "The key is `vanillabp.adapters.<id>.allow-listeners`",
  says "A value written there anyway gets one guiding warning which names the three levels that
  work, and the boot goes on." It now reads "A value written there anyway ends the start, with a
  message which names the key and the three levels that work."

The rest of the decision stays as it is.

#### What was wrong

`allow-listeners` is read at adapter, workflow-module and workflow level, but not at task level. A
value set at task level changed nothing, and the start only wrote one WARN about it and went on. So
the application ran with a value it did not ask for, and a WARN in a long start log is easy to
miss.

#### The decision

A value of `allow-listeners` at task level ends the start, on both platforms. The message names
each such key as it was written, the three levels where the key works, and why there is no task
level for it. It tells the reader to move the value to one of the three levels, or to remove it.

Both platforms bind the key at task level, because the task level shares its keys with the other
levels. So the adapter sees it on both platforms, and it is the adapter which ends the start, while
it builds the deployment service. On Quarkus this needs no build step: Quarkus does not end the
start on this key by itself. And the check at runtime also sees a key which an environment variable
or another configuration source of the running application brings.

The Camunda 8 adapter does the same for `allow-listeners` and `allow-connectors`, with the same
wording.
