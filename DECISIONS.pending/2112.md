# Pending decisions of story 2112

## The deployment source is `<adapter id>:<workflow module id>`

Decided by the maintainer on 2026-11-10.

This adapter wrote `camunda7:<adapter id>` into the source of every deployment. The prefix said
nothing, because every deployment on this engine is a Camunda 7 deployment, and the adapter id is
mostly `camunda7` anyway. Now the source is `<adapter id>:<workflow module id>`. The deployment
name stays the workflow module id.

In Camunda 7 the source matters only to the duplicate filter, which compares a model with the last
deployment of the same name, source and tenant. Otherwise Cockpit and the deployment query only
show it. A version 1 application gets a new version on its first start either way.

Inside the adapter, the check of what the engine holds tells a VanillaBP deployment by its source.
It used to look for the prefix `camunda7:`. Now it looks for a source which ends with `:` and the
deployment's name. `Camunda7DeploymentSource` holds the format and the check.

Where this changes an existing entry: decision 17, two sentences. It said that this adapter writes
"the adapter type and the adapter id", and that a source which "names a Camunda 7 adapter of
VanillaBP" makes a report uncertain. Both now describe the new format. Nothing else of decision 17
changes. This needs no number of its own.

- `Camunda7DeploymentSource`
- `Camunda7IdentifiersTheEngineHolds.HolderDescriptions#holderOf`

- `README.md`, section about what the engine already holds

## Addendum to decision 22: a model version 1 deployed carries no note, so the core is asked

Proposed by story 2112. Needs the maintainer's yes. Default if there is no answer: keep it, because
a migration of running workflows must not be mandatory.

Decision 22 says that a call activity whose called process continues the caller's workflow
aggregate gets the note `vanillabp:sameWorkflowAggregate`, and that the multi-instance walk trusts
the deployed model: where a call activity names its called process and has no note, the walk ends
there. That holds for a model this adapter prepared. Version 1 deployed the file as it was. So a
workflow version 1 started, which runs on its version after the upgrade, has call activities
without the note. Without this addendum, a task of a called process lost the iteration of its
caller. `Camunda7UpgradeFromVersionOneIT` measured it: the task ended in an incident with "No
multi-instance context named 'UFV_CallEach' was supplied by the BPMS adapter". Version 1 reported
that level where both processes were in one file.

So a missing note means "no" only where a VanillaBP adapter deployed the calling model. The
deployment source says so: it ends with `:` and the deployment's name (see the entry above). For a
call activity of any other model, the walk asks the core while the workflow runs, the same way it
asks for a call activity which names its process in an expression. The answer is kept per
deployment in `Camunda7TaskRegistry`, so the engine is asked once per deployment.

Where it would change an existing entry: decision 22, the sentence "Where the model spells out the
called process, the answer of the deployment stands." It stays true for every model this adapter
deployed. The addendum adds the case of a model which nobody answered for. Proposed text, as a new
paragraph after "A workflow standing in an older version keeps the answer that version was deployed
with.": "A model which version 1 deployed was never prepared, so none of its call activities has a
note. The source of its deployment tells it apart. For its call activities the core is asked while
the workflow runs, as for an expression."
